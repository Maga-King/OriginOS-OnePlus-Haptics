# 借鉴 OPPO 的混音规则

我们提取的一加官方 AAC 库可以确认有两组逻辑命令队列。`VibratorMixer::get_performer_dimension()` 先查命令是否属于已有队列，再找空队列；两组均占用或不满足条件时会拒绝。`MixController::stream_mix_data()` 对齐采样位置，把一路样本累加到另一路缓冲区，最终由同一个输出过程发送到驱动。

这证明的是该官方样本的混音结构，不能推断每一种官方通知、按键都通过同一入口，也不能把它说成无限并发。ColorOS 框架样本另有 RichTap 来源识别和是否停止旧 pattern 的规则；没有读取这些规则的 vivo 框架不能只复制 OPPO JSON 就生效。

插件 `0.1.2` 借鉴来源识别和分别取消的思路：

- 已有通知、铃声、闹钟等普通 `SingleVibrationSession` 不被新短触感取消。
- 被优先级挡住的 TOUCH、硬件、输入法或手势单个预设效果，可以送入混音。HAL 继续限制短路最长 120 ms。
- 新短触感替换上一个短触感；不会积压一串过期按键。
- 按 token 与 usage 取消对应短路。正常会话的取消只结束正常波形；两路最后合成一路 PCM。
- 不介入 Vendor/External 会话；保留权限、AppOps、设置与勿扰判断。

这仍然是被拒绝后由插件送入 HAL 的独立短触感，并没有改成框架原生的多个正常会话。框架会话历史仍能看到原请求被拒绝，插件日志记录 `parallel` 的结果和 `currentUsage`。`currentUsage=49` 是通知，33 是铃声，17 是闹钟。

只去掉优先级拒绝会导致框架取消旧会话，或者把短触感放到下一个会话等待，并不能实现混音。要直接接纳成第二个正常会话，还要重做启动、完成回调与取消的归属。这个版本没有假称完成该改造。

HAL `0.3.0-demo3` 同时包含 [长震动输出修复](STREAM_FIX.md)。插件更新后必须完整重启；热换 HAL 不会重载 system_server 中已加载的旧插件。
